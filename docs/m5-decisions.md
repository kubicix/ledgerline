# M5 implementation decisions

These decisions keep their rationale and what each costs if wrong. This file covers
Milestone 5 part A (M5-T01 to M5-T06); part B (M5-T07 to M5-T11) appends to it.
Entries that a later fix reversed say so; the current state is stated in the entry.
The M4 equivalent is [M4 decisions](m4-decisions.md).

## Rulings

Pre-flight:
- Setup: Ruling: The handoff corrections C1 to C4 are binding and are listed under "Spec deviations recorded, spec unchanged". Cost if wrong: see that section.
- Setup: Ruling: Implementers never commit. The orchestrator re-runs the Prove command and the build, ticks Done, and commits once per task with the plan's message and no trailers. A combined review of the base-to-head range follows, and review fixes land as separate `fix:` commits. Cost if wrong: a task commit holds unreviewed code until the fix commit (history only).

Task 1 (Kafka and MongoDB in Compose and the test fixture):
- Task 1: Ruling: The Kafka test container binds a fixed host port, and the module rewrites the advertised listener on each start. `StopKafkaAsync` and `StartKafkaAsync` therefore keep `KafkaBootstrapServers` valid across a real broker stop, the same method the RabbitMQ stop relies on. Pause and unpause would not stop the broker. Cost if wrong: the outage test hangs after the restart; switch to pause and unpause. A port race at start time is rare but possible.
- Task 1: Ruling: Kafka readiness is an exec of `kafka-broker-api-versions.sh` inside the container, not the module's log line, because on a restart the old "RUNNING" line is already present. Cost if wrong: about 1 to 2 s of JVM start per probe.
- Task 1: Ruling: `KafkaBootstrapServers` and `MongoConnectionString` are synchronous `Lazy<>` properties, so a test that never touches them starts neither container. A start exception is cached by the `Lazy<>` (acceptable). Cost if wrong: none.
- Task 1: Ruling: Compose publishes Kafka on host port 9094 (external listener, advertised as `localhost:9094`) and MongoDB on 27017, like Postgres, RabbitMQ and Redis. Cost if wrong: a host port conflict for a developer; delete the two `ports:` entries.
- Task 1: Ruling: `KAFKA_AUTO_CREATE_TOPICS_ENABLE=false` in Compose. `kafka-init` creates the three event topics (6 partitions, `retention.ms=-1`) and the dead-letter topic (see C4). Anything that produces to an unlisted topic on the Compose broker now fails. Testcontainers brokers keep the module default, and the tests create their topics explicitly. Cost if wrong: a producer to a new topic needs the topic added to `kafka-init`.
- Task 1: Ruling: MongoDB in Compose has no authentication, so there is no credential in the repository. The Testcontainers module generates its own user and password at runtime. Cost if wrong: none for a development stack.
- Task 1: Ruling: `MongoDB.Driver` is pinned at 3.14.1 (the ADR said 3.14.0, same line; ADR 0000 updated). `Confluent.Kafka` is 2.16.0. `Testcontainers.Kafka` and `Testcontainers.MongoDb` stay at 4.16.0 to match the other Testcontainers packages, although 4.17.0 exists. Both new Testcontainers packages and the MongoDB server (SSPL, same stance as Redis) have ADR 0000 rows. Cost if wrong: none.
- Task 1: Ruling: `Confluent.Kafka` and `MongoDB.Driver` are referenced only by the Messaging integration test project, and `Ledgerline.Testing` references only the two Testcontainers modules, so other test modules do not pick up librdkafka. Cost if wrong: none.

Task 2 (outbox transport and the Kafka publisher):
- Task 2: Ruling: The outbox gets a second transport with one hosted `OutboxRelay<TDbContext>` that runs one loop per registered `IOutboxPublisher`, each filtering on its own `transport` (head gate, batch select, backoff state, pending count). A `HostAbortedException` in one loop stops the whole relay, as before. The relay refuses to start with zero publishers or two for one transport. Cost if wrong: a refactor into one hosted service per transport; `FailureScenarioTests` relies on exactly one hosted relay.
- Task 2: Ruling: `IOutboxRouting` returns all rows, RabbitMQ first. `EfOutbox` takes it as an optional fourth constructor parameter (default RabbitMQ only), so existing call sites are unchanged. `EfOutbox.Enqueue` now throws `ArgumentNullException` for a null message. Cost if wrong: a Kafka-only event would need a change to the default routing, which section 0 of the handoff rules out.
- Task 2: Ruling: The wake-up is a per-loop subscription (`OutboxSignal.Subscribe()`), so a commit wakes every transport loop. The legacy single permit and `OutboxSignal.WaitAsync` were removed in fix round 1 (commit 321a559), because the unused permit threw and caught `SemaphoreFullException` on every commit in production. `Notify` now releases only the subscription permits and returns early when one is already held. Cost if wrong: none for behaviour; callers must subscribe.
- Task 2: Ruling: The RabbitMQ publisher is registered with `TryAddEnumerable`, because `configure` runs before the runtime registration and `TryAddSingleton` would let a Kafka publisher registered first drop it. A test that replaces the publisher must use `RemoveAll<IOutboxPublisher>()` or `Replace`. Cost if wrong: an `IOutboxPublisher` registered after `AddLedgerlineMessaging` no longer wins; the relay refuses the duplicate transport at start.
- Task 2: Ruling: `MessagingBuilder` keeps its public surface, and the Kafka project reaches `Services`, `Types`, `Configuration` and the trace-parent helper through `InternalsVisibleTo`. This is the repository's first one. Cost if wrong: a third-party transport package could not extend the builder; making four members public fixes that.
- Task 2: Ruling: Kafka options come from the `IConfiguration` passed to `AddLedgerlineMessaging` (`Messaging:Kafka:BootstrapServers`, required once any `AlsoPublishToKafka*` call is made; `Messaging:Kafka:MessageTimeoutMs`, default 5000), and `KafkaOptions` is registered with `TryAddSingleton` so a test can supply its own. Nothing Kafka-related is registered until the first `AlsoPublishToKafka*` call, so librdkafka is not loaded with the switch off. Cost if wrong: small.
- Task 2: Ruling: Producer settings are `EnableIdempotence = true`, `Acks = All`, `MessageTimeoutMs = RequestTimeoutMs = 5000` and `LingerMs = 0` (the relay awaits each delivery inside the transaction). Only the host token is passed to `ProduceAsync`; cancelling it stops the wait but does not withdraw the record, so the row stays unprocessed and is produced again after a restart (a duplicate within at-least-once). A row is marked processed only on `PersistenceStatus.Persisted`; `PossiblyPersisted` counts as a failure and may duplicate. Cost if wrong: 5 s may be tight for a slow broker, giving more retries and duplicates that the inbox and idempotent projections absorb.
- Task 2: Ruling: A fatal producer error (`KafkaException` with `Error.IsFatal`) makes the next produce build a fresh producer. No test can trigger a fatal error on demand, so the rebuild path is unverified. Cost if wrong: see deferred finding F1 for the same class of problem in the Reporting dead-letter producer.
- Task 2: Ruling: Disposal flushes for at most 2 s and then disposes. `Host_stops_promptly_while_kafka_is_down` bounds stop at 5 s and stop plus dispose at 10 s with a 60 s message timeout, so ignoring cancellation fails it (checked by mutation in fix round 1). Cost if wrong: up to 2 s added to shutdown while Kafka is down, inside the 25 s `ShutdownTimeout`.
- Task 2: Ruling: The metric tag `ledgerline.transport` is on `ledgerline.outbox.lag` and `ledgerline.outbox.pending`, including the RabbitMQ series, because two loops writing one gauge series would overwrite each other. The dashboards are unchanged and aggregate across both transports once Kafka is on (the Helm copy was out of scope). Cost if wrong: a dashboard follow-up.
- Task 2: Ruling: Span `messaging.system` is the row's transport. Kafka spans are named `publish <topic>`; RabbitMQ spans are unchanged. Cost if wrong: cosmetic.
- Task 2: Ruling: There is no index on outbox `transport`, because a schema change is forbidden in part A. A long Kafka outage adds a linear scan of the pending Kafka rows to each RabbitMQ poll. Cost if wrong: RabbitMQ poll latency grows with the Kafka backlog; the fix is a partial index `(transport, sequence) WHERE processed_at IS NULL` in a later migration.
- Task 2: Ruling: Per-key Kafka order holds per relay instance only. With several replicas, `SKIP LOCKED` lets two instances produce rows of one key from different batches (the ADR 0003 limit). Replicas stay at 1, and the projections tolerate disorder (statements replace by `_id`, timelines are guarded by `occurredAt`, totals by message id). Cost if wrong: out-of-order records per key with more than one replica.
- Task 2: Ruling: A Kafka row whose type has no topic mapping, or whose key function throws, retries forever with backoff and blocks the head of its own transport loop, like an unroutable RabbitMQ row. The RabbitMQ loop is not affected. Cost if wrong: a stuck Kafka transport until the row is fixed.
- Task 2: Ruling: Expanded records get UUIDv5 message ids over (the RabbitMQ row's message id, the record's 0-based index), implemented by hand with big-endian bytes (see C2). CA5350 is suppressed on that one line with a comment. Cost if wrong: none; the ids stay deterministic whatever the name is.
- Task 2: Ruling: Two files outside the task list changed: `OutboxRelayTests.cs` (the fake publisher implements the new `Transport` member) and `ServiceIsolationTests.cs` (the Kafka assembly joins the production assemblies and the list Gateway and BankSimulator must not reference). Nothing was weakened. Cost if wrong: none.
- Task 2: Ruling: `KafkaOutboxTests` runs in the non-parallel "Broker lifecycle" collection, so a Kafka stop does not race other classes. Tests create topics with `AdminClient` (6 partitions) and rely on no auto-creation. Cost if wrong: none seen.

Task 3 (Accounts and Payments publish to Kafka):
- Task 3: Ruling: `AccountOpened` is routed unchanged, including `contactEmail`, to `ledgerline.accounts.events.v1`. See the spec deviations and open owner item 1. Reporting must never store or log the email. Cost if wrong: personal data in an extra store; the fix is a redacted record type through `AlsoPublishToKafkaExpanded`.
- Task 3: Ruling: The switch `Messaging:Kafka:Enabled` defaults to `false` in code (`GetValue<bool>`) and is read in each service's `Program.cs` inside the `AddLedgerlineMessaging` configure lambda, because neither service has an `appsettings.json`. Compose and Helm are untouched. Cost if wrong: none.
- Task 3: Ruling: The routes are Accounts: `JournalEntryPosted` expanded into `JournalEntryLinePosted` on `ledgerline.ledger.entries.v1`, and `AccountOpened` on `ledgerline.accounts.events.v1`; Payments: `PaymentAuthorized`, `PaymentCaptured`, `PaymentCompleted`, `PaymentVoided`, `PaymentFailed` and `PaymentRefunded` on `ledgerline.payments.events.v1`. No command and no saga reply is routed. Every routed type is enqueued with its concrete static type, because routing keys on `typeof(T)`. Cost if wrong: an event enqueued through a base type would not reach Kafka.
- Task 3: Ruling: `JournalEntryLinePosted` has the entry fields, then the line fields, then `LineNo` last (1-based, equal to the ledger's own `line_no`), and a static `From(JournalEntryPosted)` that holds the numbering rule next to the type. Cost if wrong: move the helper into Accounts (one line in `Program.cs`).
- Task 3: Ruling: Kafka keys are `Guid.ToString()` (lowercase hyphenated) for both `accountId` and `paymentId`. Cost if wrong: changing the format later changes partitioning and breaks per-key order across the change.
- Task 3: Ruling: `SagaRunner.EnqueueCommand` and `RefundRecovery.Schedule` snapshot the message ids in the change tracker before their own enqueue and then take `.Single` over the new rows, so event rows (RabbitMQ plus Kafka) enqueued earlier in the unit of work do not break them. Commands have no Kafka route. This was reasoned from the code; no switch-on test enqueues an event and a command in one unit of work. Cost if wrong: a command type with a Kafka route would make `.Single` throw.
- Task 3: Ruling: No transport filter was added to the pending-row queries in `tests/Ledgerline.SystemTests/Harness/SystemQueries.cs` and `tests/Ledgerline.Payments.IntegrationTests/TimeoutTests.cs`. With the switch off there are no Kafka rows, and with it on, "zero pending" means everything was delivered. Cost if wrong: a Phase 2 system test with Kafka down would see a non-zero pending count.
- Task 3: Ruling: `ServiceHost.StartAsync` and `StartOnDatabaseAsync` take an optional `settings` parameter applied with `UseSetting`, because the switch is read before `builder.Build()` and `ConfigureAppConfiguration` values arrive too late. Environment variables are process-wide and tests run in parallel. `MerchantScenario` got an optional `paymentSettings` parameter. Cost if wrong: if a future `WebApplicationFactory` stopped forwarding host configuration as arguments, the Kafka-enabled tests would fail loudly because the routes would be missing.
- Task 3: Ruling: Two tests beyond the named ones: `Account_opening_produces_a_kafka_record_keyed_by_account`, and a `With_kafka_disabled_no_kafka_rows_are_written` test in each project. Cost if wrong: about 10 s of test time.
- Task 3: Ruling: A replayed ledger operation calls `ReplyAsync` only and does not publish the lines again, so a replay never puts duplicate lines on Kafka under new message ids. Cost if wrong: none.

Task 4 (Reporting service, consumer loop, account statements):
- Task 4: Ruling: Only transient failures are retried without limit: connection, timeout, server selection, failover (not-primary, node recovering, full or paused pool, `RetryableWriteError`, `TransientTransactionError`) and, after fix round 1, write-concern failures (`MongoWriteException` with a null `WriteError` and a `WriteConcernError`, and the matching `MongoBulkWriteException`). Everything else is poison, including a `MongoWriteException` with a `WriteError` such as a duplicate key, and is dead-lettered after 5 attempts. Cost if wrong: a transient condition outside the list is dead-lettered and its read-model update is lost until a rebuild.
- Task 4: Ruling: Poison attempts run in memory with backoff (5 attempts, waits of 200, 400, 800 and 1600 ms at the defaults), while transient failures seek back and re-consume. The attempt count does not survive a restart or rebalance. If the dead-topic produce fails, the record is rewound and its attempt count restarts at 1. Cost if wrong: a broker outage delays the dead-lettering of a poison record by one round.
- Task 4: Ruling: This reverses the original "commit at batch end" design. A batch now ends at a dead-lettered record, whose offset is committed at once, and the rest of the batch is sought back and consumed again with no backoff. So one batch retries at most one poison record, and about 100 poison records can no longer exceed `max.poll.interval.ms`. A failed commit is logged and rethrown, and the outer loop closes the consumer and builds a new one. Cost if wrong: a poison record forces a seek and a re-fetch of the rest of its batch (a rare path); a commit failure, including a `REBALANCE_IN_PROGRESS` that a retry could survive, costs a heavier recovery with idempotent re-applies.
- Task 4: Ruling: `max.poll.interval.ms` stays at the librdkafka default of 300 s. The worst case between polls at the defaults is about 50 s. Cost if wrong: an operator who raises `RetryMaxDelayMs` past about 60 s could exceed the interval on the poison path; no guard enforces this (documented in the class summary).
- Task 4: Ruling: `AccountStatementDocument.From` rejects an empty `JournalEntryId` or `AccountId`, `LineNo < 1`, or an empty `EntryType`, `Direction` or `Currency`, because System.Text.Json leaves missing fields at their defaults and `{}` would otherwise upsert a zero id. `PaymentId` is not validated. Cost if wrong: a legitimate line with an empty value in one of those fields would be dead-lettered; the ledger never emits one.
- Task 4: Ruling: `postedAt` is truncated to milliseconds (BSON dates). It is deterministic, so the rebuild comparison is unaffected. Cost if wrong: a client comparing with the ledger's microsecond timestamp sees a sub-millisecond difference.
- Task 4: Ruling: Consumer settings live in `Reporting:Kafka:*`, not `Messaging:Kafka:BootstrapServers`, because Reporting does not use the Messaging Kafka options. Part B sets `Reporting__Kafka__BootstrapServers` for Reporting. Cost if wrong: rename the constants in `ConsumerOptions`.
- Task 4: Ruling: MongoDB settings are `ConnectionStrings:Mongo` plus a separate database name key, because the Testcontainers connection string has no path (a path would change `authSource`). The client keeps the driver's 30 s server selection timeout. Cost if wrong: slower outage detection; tune `serverSelectionTimeoutMS`.
- Task 4: Ruling: Indexes are created on the loop thread before subscribing and retried instead of failing startup, so the host reports started (readiness 503) while MongoDB is unreachable. Cost if wrong: none; this matches reporting.md section 7.
- Task 4: Ruling: Consumer `Close` is bounded at 10 s, and a consumer whose close timed out is not disposed (a native handle leaks at process exit at worst). There is no `PartitionsRevoked` handler, because commits are synchronous after every batch on the consume thread. Cost if wrong: occasional duplicate applies after a rebalance, which are harmless.
- Task 4: Ruling: The dead-letter record carries only its five listed headers, not the original ones such as `traceparent`. Cost if wrong: a dead record links to its trace only through the envelope's own `traceParent` field in the value.
- Task 4: Ruling: The test host is a `WebApplicationFactory` in the Reporting test project (`ReportingHost`), because `Ledgerline.Testing.ServiceHost` is Postgres and DbContext specific. Cost if wrong: none for the product.

Task 5 (payment timelines and merchant daily totals):
- Task 5: Ruling: `appliedMessageIds` is pushed with `$push: { $each: [id], $sort: 1, $slice: -1000 }`. This reverses the original ruling, which kept the spec's `$push` and `$slice` and compared the array as a set in the rebuild proof. With the sort, message ids (UUIDv7 lowercase strings) keep the newest 1 000 by message time whatever order the partitions were consumed in, so the rebuild comparison is strict. The driver's `PushEach` cannot express a scalar `$sort`, so the operator is built as a `BsonDocumentUpdateDefinition`. Cost if wrong: a redelivered message whose id sorts below the newest 1 000 of its document is counted again (the same exposure as the spec's cap).
- Task 5: Ruling: On `E11000` from a guarded upsert, the projection retries the same write once without the upsert. For an already-applied message the retry matches nothing; for two writers inserting one new `_id` at once, the loser's message is applied instead of lost. Cost if wrong: one extra no-op round trip per duplicate; revert by deleting the retry line in each catch. The concurrent-insert path is reasoned from driver semantics, not tested.
- Task 5: Ruling: Timelines use two guarded writes, the second on every apply so a crash between them heals on redelivery: an `events.messageId $ne` push with upsert, then a summary `$set` guarded by `updatedAt: { $not: { $gt: occurredAt } }`. `updatedAt` is event time, never processing time. Cost if wrong: two events of one payment inside the same millisecond both apply in arrival order.
- Task 5: Ruling: Daily totals cover only `kind = MerchantPayment`, with the UTC date of `occurredAt` as the day and `_id = "<merchant>:<day>:<currency>"`. All counters and amounts are Int64. Cost if wrong: an API client that wants `int` converts.
- Task 5: Ruling: Invalid payment events (a missing payment id, customer, destination, kind, currency or `occurredAt`, or a failed event without `status`) are poison and are dead-lettered after 5 attempts. Cost if wrong: a legitimate event with an empty value would be dead-lettered; Payments never emits one.
- Task 5: Ruling: A `payment-refunded` event before any other creates a document without `status`, which appears with the next event. Cost if wrong: none.
- Task 5: Ruling: Beyond the task list, `Projections/PaymentEvent.cs` (one parser for the six payment contracts, shared by both projections), two collection entries in `MongoCollections.cs` and two registrations in `Program.cs`. Cost if wrong: none.
- Task 5: Ruling: The 1 001-message cap test applies messages directly through `MerchantDailyTotalsProjection` on a throwaway database, not through Kafka, because 1 001 sequential records would only slow it. Cost if wrong: the cap is not proven through the consumer loop.

Task 6 (Reporting API, rebuild and consistency proofs):
- Task 6: Ruling: Lag is the age of the oldest held-but-unapplied record. If the loop holds no record of a partition that is behind, it counts from the last applied record (an upper bound), and with nothing applied it is 0. Lag reads 0 when caught up, so a Kafka outage after catch-up shows 0 although the data may be stale. It measures consumer lag, not freshness. Cost if wrong: the header understates staleness during a broker outage; detecting it needs a reachability or time-since-last-fetch signal the spec does not define. The same applies right after a start or rebuild, until the first batch is taken.
- Task 6: Ruling: The `X-Read-Model-Lag-Seconds` header is on every response, including health checks and 401. Cost if wrong: none.
- Task 6: Ruling: A non-owner, a non-party and an unknown id all get 404, as Accounts' `GET /accounts/{id}` and Payments' `GET /payments/{id}` do, and ownership is checked before parameter validation. Cost if wrong: a client cannot tell "not yet replicated" from "not yours", which is intended.
- Task 6: Ruling: `from` and `to` are inclusive on both endpoints (`postedAt` instants, `yyyy-MM-dd` days). Cost if wrong: one boundary line or day too many.
- Task 6: Ruling: Response shapes: the statement is a `Page` (`items`, `nextCursor`), the daily totals are a bare JSON array without a limit or pagination (like Accounts' `GET /accounts`), and the timeline names `_id` as `paymentId`. The statement cursor is base64url JSON `{at, id}` (Payments' pattern), because the order needs two keys. Cost if wrong: renames only, but part B and M6 clients bind to these; a very wide daily-totals range gives a large response.
- Task 6: Ruling: A new index `merchant_daily_totals { merchantAccountId: 1, day: 1 }` was added, which the spec does not name (Task 5 suggested it). Cost if wrong: one more index write per daily-total update.
- Task 6: Ruling: The statement index `{ accountId: 1, postedAt: -1 }` is unchanged (spec and Task 4 pin it), so each page of at most 101 documents is sorted in memory for the `_id` tie-break. Cost if wrong: negligible at this page size.
- Task 6: Ruling: Rebuild order is: check that the consumer group has no active members, drop `account_statements`, `payment_timelines`, `merchant_daily_totals` and `account_owners`, reset the group's committed offsets to each partition's earliest offset (not a literal 0, so it stays correct if retention is ever finite; with `retention.ms=-1` the test asserts 0), then recreate the indexes and exit. Resetting before the drop would risk double counting beyond the 1 000-id window. Cost if wrong: if a step after the drop fails, run the command again; starting Reporting in between gives empty collections behind old offsets, a stale read model and not a double count.
- Task 6: Ruling: `RebuildCommand.RunAsync` is covered by the test with the host's settings; the `rebuild` mode in `Program`'s argument parsing was not run as a process. Cost if wrong: an argument-parsing slip would show only when the command is run for real.
- Task 6: Ruling: The Q3 proof makes the postings strictly sequential and fails on a `postedAt` tie at an account's newest line instead of tolerating one. No tie occurred. Cost if wrong: a residual flake source if two postings share a timestamp.
- Task 6: Ruling: `Ledgerline.Reporting.IntegrationTests` references Accounts, to run the ledger in-process for Q3. Cost if wrong: that test project also rebuilds when Accounts changes.
- Task 6: Ruling: `KafkaConsumerLoop.cs` changed by five lines for the `LagTracker` hooks, and `MongoCollections` gained `CreateClient` and `OpenDatabase`, shared by `Program` and `RebuildCommand`. Cost if wrong: none.

## Spec deviations recorded, spec unchanged

`docs/design.md`, `docs/specs/*`, `docs/testing.md` and the ADRs were left as written, except for ADR 0000 version rows.

- C1, the per-line ledger record type (M5-T03): `reporting.md` section 2 says the value on `ledgerline.ledger.entries.v1` has type `accounts.event.journal-entry-posted.v1`, one record per line. The plan's new type `accounts.event.journal-entry-line-posted.v1` (`JournalEntryLinePosted`, entry fields plus one line and `lineNo`) is used, because the payload differs from `JournalEntryPosted` and `MessageTypeRegistry` maps one type name to one CLR type. One record per line, the line's `accountId` as key and `lineNo` in the payload hold as in the spec. Applied in Task 3; Reporting's statement projection dispatches on this name.
- C2, deterministic ids of expanded records (M5-T02, M5-T03): the envelope `messageId` of each expanded record is derived from the source, not generated at publish time, so a relay retry after a partial produce does not look like new records. It is a UUIDv5 over the RabbitMQ row's message id and the record's 0-based index, not the UUIDv7 that `building-blocks.md` section 2 asks for. The non-expanded case keeps a fresh UUIDv7, and `Event_routed_to_both_transports_writes_two_outbox_rows_with_different_message_ids` is unchanged. Task 3 proves the ids equal the Kafka outbox row ids and are recomputable from the RabbitMQ row.
- C3, Reporting readiness (M5-T04): `design.md` section 11 says readiness checks the service's own database and its broker connection, while `reporting.md` section 7 says Reporting serves stale data when Kafka is down. Reporting's readiness checks MongoDB only, so a Kafka outage does not take the read API out of rotation. Reporting never calls `AddLedgerlineMessaging` or `AddLedgerlineInbox` (which would register the RabbitMQ `broker` check) and uses only the envelope and serializer types. Liveness has no checks.
- C4, the dead-letter topic (M5-T01, M5-T04): `reporting.md` section 7 names `ledgerline.reporting.dead.v1`, while M5-T01 says `kafka-init` creates "the three topics". `kafka-init` creates the three event topics (6 partitions, `retention.ms=-1`) and also the dead topic (1 partition, same retention). Verified with `kafka-topics.sh --describe`. No topic relies on broker auto-creation.
- Task 5, `$sort: 1` added to the spec's `$push` and `$slice` shape for `appliedMessageIds` (`reporting.md` section 4), so the array keeps the newest 1 000 ids by message time regardless of consumption order and the rebuild comparison is strict.
- `account-opened` (with `contactEmail`) is relayed to `ledgerline.accounts.events.v1`, although `accounts.md` says only Notifications consumes it. `reporting.md` section 5 mandates the topic and the event, and the `accounts.md` statement predates Phase 2. Reporting reads only `accountId` and `ownerId` and never stores or logs the email. See open owner item 1.
- Reporting readiness is MongoDB only against `design.md` section 11 (C3, above), and expanded message ids are UUIDv5 against the envelope's usual UUIDv7 (C2, above); they are repeated here so a reader of the spec finds all deviations in one list.
