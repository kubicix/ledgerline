# M2 implementation decisions

These historical decisions preserve their rationale and the cost if wrong.
Read [the final review checkpoint](m2-review.md) for findings that supersede an
earlier decision, especially 204 admin idempotency and Risk timestamp semantics.

- Ruling: Reuse the existing managed linked worktree on codex/milestone-2, created from merged origin/main. Do not create a second worktree. Cost if wrong: the directory name still says milestone-1, but branch and base are correct.
- Ruling: Task scripts parse Task N instead of M2-TNN; keep equivalent manual brief/BASE/completion bookkeeping, with Task 1..19 referring to M2. Cost if wrong: manual tracking can drift.
- Task 1: Ruling: Generate a random symmetric signing key per test process and inject it through TestKey configuration; no reusable signing credential is committed. Cost if wrong: test tokens are intentionally valid only within their process.
- Task 1: Ruling: Keep the existing ICurrentUser contract and ServiceHost client API; replace only their auth implementation. Preserve the exact three-argument TestTokens.Create and add a five-argument overload for audience/expiry regressions. Cost if wrong: tests have one additional helper overload.
- Task 1: Ruling: Use a fixed public Keycloak hostname with dynamic internal backchannel discovery, so host-issued tokens and container JWKS fetches agree. The official Keycloak hostname guide specifies this split. Cost if wrong: local hostname settings must be adapted for other deployment addresses.
- Task 1: Ruling: Seeded Keycloak users have one wallet per type/currency, so smoke requests use stable idempotency keys and are repeatable against retained data. Cost if wrong: smoke replays its prior completed operations instead of creating new money on every invocation.
- Task 1: Ruling: Update the README authentication/quick-start wording alongside the auth change instead of leaving it inaccurate until T19. Cost if wrong: the documentation changes span two tasks.
- Task 1: Ruling: The cold Compose proof exposed PostgreSQL health accepting its temporary Unix-socket-only initialization server. Logs show migrations started at 17:32:16/18 before TCP began at 17:32:24. Require pg_isready over 127.0.0.1 TCP instead; do not add migration retries. Cost if wrong: readiness waits for actual network availability, as application connections require.
- Task 1: Ruling: Populate firstName and lastName on synthetic realm users because Keycloak required profile fields prevented direct-grant login (invalid_grant: Account is not fully set up). Cost if wrong: demo users carry additional synthetic profile fields.
- Task 1: Ruling: Explicitly retain the Keycloak basic client scope with profile/email. A real token had correct issuer/audience/roles but no sub, and the API correctly rejected it. Keycloak maps sub through basic. Cost if wrong: additional standard identity claims accompany these development tokens.
- Task 2: Ruling: Add the plan-required StackExchange.Redis direct Web reference at the existing central version. Use a typed IIdempotentResource DTO marker to capture the resource ID without reflection or serializing the HTTP result; JSON shape is unchanged. Cost if wrong: later successful resource DTOs must opt in to the marker.
- Task 2: Ruling: Use atomic Lua compare-and-set for begin/complete/release, with request-scoped lease hashes so cleanup cannot delete another request's value. Preserve database replay loading and current representations. Cost if wrong: Redis stores only the spec's fixed 24-hour metadata, never response bodies.
- Task 2: Ruling: M1 concurrent POST tests allowed only success because Redis was deferred; update them to accept the M2-specified 409 with Retry-After and replay after completion, retaining one-row and identical-ID assertions. Cost if wrong: callers must retry in-progress responses as the spec requires.
- Task 2: Ruling: The outage and failed-validation tests already passed before Redis existed, proving existing database fallback and key reuse. Three new Redis assertions failed for their intended reasons before implementation. Cost if wrong: the regression tests alone cannot distinguish no accelerator from a working fallback; cached-state and in-flight tests provide that distinction.
- Task 4: Ruling: Recheck an existing decision after acquiring the daily-total row lock, so replicas that both miss the initial lookup replay the first committed result instead of counting twice. Cost if wrong: one additional lookup per new evaluation.
- Task 4: Ruling: Normalize decision timestamps to PostgreSQL microsecond precision before both storage and first publication. The exact replay test failed because first JSON retained 100ns ticks that PostgreSQL truncated. Cost if wrong: timestamps lose sub-microsecond precision, while all replies remain identical.
- Task 4: Ruling: EF generated migration source is marked auto-generated, matching M1 migrations and excluding generated array literals from handwritten-code analyzer suggestions. Existing EF CLI 10.0.6 generated the 10.0.15 model successfully with a tool-version advisory; do not upgrade global tools without need. Cost if wrong: future migration generation may require a tool upgrade.
- Task 5: Ruling: Skip a known-disconnected Redis multiplexer immediately, while still catching operation-time Redis failures; emit the specified fallback metric and warning, and count database decisions. Cost if wrong: an operation during reconnect may use the slower database path.
- Task 5: Ruling: Keep the default rule cache TTL at 10 seconds and permit a constructor TTL override solely to prove 100ms expiry without fixed sleeps. Redis window tests pass explicit timestamps. Cost if wrong: callers constructing RuleCache directly must keep a positive TTL.
- Task 6: Ruling: Serialize each bank idempotency key with a transaction-scoped PostgreSQL advisory lock; lock authorization rows separately for competing operation keys. This works across replicas and replays before state checks. Cost if wrong: rare advisory-hash collisions serialize otherwise unrelated requests without changing results.
- Task 6: Ruling: Compare bank replay JSON structurally, matching the repository contract tests. PostgreSQL jsonb reorders object keys, so the initial byte-order assertion failed despite identical IDs, timestamp and values. Cost if wrong: inconsequential JSON object ordering can differ between first response and replay.
- Task 6: Ruling: Configure the simulator API key through BankOptions and fail closed for an empty key; tests inject a random per-process key. Use the explicitly approved EF Design and Npgsql provider references without any Contracts or Messaging project reference. Cost if wrong: simulator callers must supply its separate API key, as specified.
- Task 7: Ruling: Faults apply only to mapped operation metadata and requests carrying the valid simulator API key, so invalid callers cannot consume injected faults. Buffer SuccessThenTimeout responses until after the transaction commits; a cancelled delay does not undo the bank operation. Cost if wrong: response buffering is limited to the simulator's small operation responses.
- Task 7: Ruling: Use one normalized PostgreSQL-compatible timestamp for capture/refund response and persisted operation/settlement time. The added CSV assertion failed against the original separate clock reads, which could place a boundary operation on a different settlement day. Cost if wrong: sub-microsecond precision is discarded.
- Task 7: Ruling: Timeout injection returns 504 after its configured hold if the client remains connected; it never performs the operation. Tampering affects generated rows only, and CSV fields are escaped. Cost if wrong: a client with a timeout longer than the injected hold sees a definitive 504 rather than an indefinitely held connection.
- Task 8: Ruling: Preserve the disabled-by-default M1 options and existing SagaInput variants; extend optional snapshot fields and typed effects for bank IDs and ClearCardToken. Persistence of these effects remains T12. Cost if wrong: pure decisions cannot enable runtime bank flow until its planned runner/handlers are wired.
- Task 8: Ruling: Expose BankCompensationMaxAttempts with default 8 so the specified cap can be proven at attempt 9 when the limit is raised. Retry decisions schedule 2^snapshot.StepAttempt seconds, capped at 300, exactly matching the plan's examples. Cost if wrong: later runner attempt accounting must preserve this definition.
- Task 8: Ruling: Preserve the original ledger failure through compensation and use BankDeclined:<code> for capture declines as for authorization declines. Stable payment CreatedAt is an optional snapshot input for EvaluateRisk; the runtime populates it in T12. Cost if wrong: downstream reason-code consumers must accept this declared prefix for both bank decline stages.
- Task 9: Ruling: Bring forward only the exact ReserveFunds/CaptureFunds/ReleaseFunds contracts from T10 and PaymentAuthorized/PaymentCaptured/PaymentVoided contracts from T14, with samples. The pure saga cannot emit types that do not exist; their handlers/endpoints stay in the later tasks. Cost if wrong: those later tasks must reuse these declarations instead of recreating them.
- Task 9: Ruling: Split merchant-specific private transition helpers into PaymentSaga.Merchant.cs to keep the step table readable; preserve one public static saga API. Add optional snapshot fields/effects and a defaulted InvalidState flag for runner wiring later. Cost if wrong: the pure class spans two files.
- Task 9: Ruling: Check merchant capture/void user commands before the final-state ignore guard, so invalid HTTP actions can return 409 while late events and expiry remain ignored. Restore the original authorization expiry after rejected capture rather than granting seven more days. Cost if wrong: a rejection after expiry schedules immediate release.
- Task 9: Ruling: Carry Requested/Expired through the existing transient failure-reason slot while Voiding, publish that as the PaymentVoided reason, then clear it on successful void. Cost if wrong: the interim payment representation uses failureReason for the pending void cause.
- Task 10: Ruling: Reuse the exact hold command contracts/samples introduced in T09. Existing AccountResponse and its queries already compute active heldMinor, so prove that behavior rather than editing it again. Cost if wrong: no duplicate contract declarations are created.
- Task 10: Ruling: Add an async-execution overload to LedgerOperationRunner while preserving its synchronous posting-builder API. Existing-operation replay happens before hold-state validation, so retries after capture still return the original reserve result. Cost if wrong: internal runner callers have one additional overload.
- Task 10: Ruling: Serialize a payment's hold lifecycle with a transaction advisory lock, then lock existing hold rows before ordered account locks. The advisory lock also covers reserve when the hold row does not yet exist. Project holds in ILedger.PostAsync and independently reconstruct all hold fields/statuses in rebuild and LedgerAssert. Cost if wrong: unrelated hash collisions only reduce concurrency.
- Task 11: Ruling: Reuse the ledger command runner for refunds. Freeze/unfreeze lock the account row and atomically append its next-version status event with an outbox notification; an already matching state returns 204 with no event. Cost if wrong: status commands rely on their declarative state/no-op semantics rather than storing separate resource rows for idempotency replay.
- Task 11: Ruling: Apply the common POST key validator and in-flight guard to admin state commands; a 204 has no resource DTO and its Redis lease is released. Preserve the spec's no-op 204 behavior. Cost if wrong: these status commands do not retain 24-hour completed-response metadata; final review should weigh that scope.
- Task 11: Ruling: Build trial balance and correlated journal counts in one SQL query, keeping the report on one database snapshot. The cached imbalance gauge is explicitly scheduled in M3-T02 and is not implemented early. Cost if wrong: the HTTP report is available before its telemetry refresh job.
- Task 11: Ruling: The new Features.Ledger namespace shadowed an existing Ledger.AccountOpened shorthand; qualify that one event type to retain the existing payload. Cost if wrong: one existing call site now uses the full namespace.
- Task 12: Ruling: Use the exact task/ADR-pinned Microsoft.Extensions.Http.Resilience 10.11.0 with only a five-second timeout strategy; no HTTP POST retry strategy. HTTP 5xx/timeouts/network errors become Unknown, then query the stable bank key before broker retry. Cost if wrong: transient failures consume messaging retries rather than hidden HTTP retries.
- Task 12: Ruling: Simulator key validation permits colon in addition to its former ASCII set, still bounded at 64 characters. Real-service HTTP keys keep their existing validator. The initial bank integration run proved <paymentId>:authorize was rejected with 400. Cost if wrong: simulator keys accept the exact separate protocol required by the payment spec.
- Task 12: Ruling: Persist the T08 bank effects and populate all existing optional snapshot fields in the runner. Reset attempts only when entering another non-None step; preserve terminal attempt history. The broad test caught a reset from 5 to 1 before this correction. Cost if wrong: terminal audit state reflects the completed step's final attempt count.
- Task 12: Ruling: Clear opaque card tokens after both successful and declined authorization, following the spec's until-authorization-completes rule. The declined-flow integration assertion failed with tok_declined retained before adding the pure ClearCardToken effect. Cost if wrong: retrying a definitively declined payment requires a new payment request.
- Task 12: Ruling: Split effect persistence from typed message dispatch after the method grew past 40 lines. Preserve the same typed outbox enqueue calls and existing M1 API. Cost if wrong: effects are dispatched across two focused private helpers.
- Task 13: Ruling: Enable Risk and bank by default in the deployed Payments service, independently configurable. Shared legacy ServiceHost fixtures explicitly configure both off; M2 flow fixtures replace those options with the full flow. Pure defaults remain unchanged. Cost if wrong: a new full-flow test must opt in rather than accidentally running the M1 path.
- Task 13: Ruling: Permit an optional compensation-timeout override for the mandated shortened integration backoff, preserving pure exponential decisions and production defaults. Apply the existing ledger timeout setting to all ledger steps. Cost if wrong: explicitly configured overrides can shorten compensation retries.
- Task 13: Ruling: Clear top-up card tokens on every terminal failure, including risk rejection/exhaustion before authorization. Both pure retention cases were watched RED before the change; the full risk-rejection flow also asserts no retained token. Cost if wrong: manual review does not retain an unused opaque token for resubmission.
- Task 13: Ruling: A status event arriving before account-opened throws for normal inbox retry instead of silently disappearing. Added a real-broker ordering regression beyond the six named tests. Cost if wrong: a permanently missing account eventually dead-letters rather than accepting a lost status change.
- Task 14: Ruling: Use real Accounts plus Payments for merchant tests and fund fixtures directly through ILedger in a transaction. Earlier command-based fixture funding sent artificial unknown-payment replies into Payments; the business merchant flows still run through real messages and ledger posting. Cost if wrong: fixture funding bypasses the bank, while each merchant test ends with independent ledger invariants.
- Task 14: Ruling: Store capture/void key, hash, owner and operation ID in the Started audit row as payments spec section 6 requires. Serialize actions by owner/key and payment row while preserving xmin concurrency checks. The cross-payment Redis-outage test first returned four 202s for one key; the owner-key lock makes only one succeed. Cost if wrong: rare advisory-hash collisions reduce concurrency.
- Task 14: Ruling: A new manual capture request after rejection needs its own deterministic operation ID, otherwise Accounts correctly replays the stored rejection forever. Derive it from paymentId plus LedgerCapture:<HTTP key>, retain it in the Started audit, hydrate it for replies/timeouts, and ignore stale replies. Automatic capture retains the original step-name ID. Clarified this exception in the spec. Cost if wrong: internal producers must distinguish a new business attempt from a transport retry; the HTTP/message wire shapes are unchanged.
- Task 14: Ruling: Raw payment locking queries explicitly select xmin, because SELECT * excludes PostgreSQL system columns and EF's wrapper otherwise failed with 42703. Cost if wrong: this service remains intentionally PostgreSQL-specific.
- Task 14: Ruling: Lock the payment before its timeout in the poller, matching HTTP lock order. A gated real-database regression proved the old timeout-first path deadlocked with capture and returned 500. Both selection stages retain SKIP LOCKED for multiple workers. Cost if wrong: a busy payment is deferred to the next poll instead of blocking another worker.
- Task 14: Ruling: Keep the default authorization TTL at seven days and allow the plan's 500ms test override through saga options. Preserve the public Task-returning runner method and expose an internal decision-returning method for HTTP InvalidState handling. Split state persistence, command dispatch and event dispatch into focused helpers. Cost if wrong: new stateful effects must be added to the appropriate typed helper.
- Task 15: Ruling: Reuse the real Accounts merchant scenario through a shared test helper; retain the gated expiry test and ledger funding protocol. A delivery gate proves the 60% concurrent-refund limit while the first refund is still Processing. Cost if wrong: these tests intentionally hold one Accounts consumer until the assertion releases it.
- Task 15: Ruling: Route RefundFunds replies to the refund saga before the parent payment's final-state guard. Lock the parent payment, then reload the refund before applying a delta, so duplicate replies cannot increment totals twice. Failed refunds leave the pending sum automatically. Cost if wrong: refund transitions for one parent serialize on that payment row.
- Task 15: Ruling: Share owner/key locking and cross-resource hash checks across payment creation, capture/void and refunds, including Redis outages. Replays return current DTOs, and the original public runner API remains intact. Cost if wrong: unrelated hash collisions reduce concurrency; all completed-key metadata remains database-backed.
- Task 15: Ruling: Record refund transitions on the parent timeline as RefundStarted/RefundCompleted/RefundFailed at Step None, with refund ID metadata, without changing the parent captured state or adding a new step enum. The audit assertion first failed with no rows. Cost if wrong: timeline clients use the explicit outcome to identify refund activity.
- Task 15: Ruling: Share the existing opaque createdAt/ID cursor between payment and refund lists; retain the exact refund DTO shape and link Accepted to the owned refund collection, the GET resource supplied by the spec. Cost if wrong: clients follow the collection to read the refund rather than a nonexistent per-refund GET route.
- Task 16: Ruling: Add an inbox-only registration/model path and condition outbox retention on the model, preserving the full messaging API. Notifications publishes nothing in M2. Cost if wrong: consumer-only services share the same runtime without a relay.
- Task 16: Ruling: Render subject/body while planning inside the inbox transaction and store durable plain text, because the binding schema has no event payload column. The sender uses that content on every retry; rendering exceptions become Failed/TemplateError. Cost if wrong: template changes do not alter already planned emails.
- Task 16: Ruling: A missing recipient owner uses the known customer ID when supplied, otherwise Guid.Empty with an empty email on the final Skipped row. A known recipient without contact email is retried then skipped. Cost if wrong: an unknown destination owner cannot see the skipped row through the own-notifications API.
- Task 17: Ruling: Keep the last command message ID and its original duration on each timeout. While unpublished, advance due time without consuming an attempt; after publication rebase the deadline from processed_at, then clear the publication marker. A duration field preserves the original backoff after deferrals, avoiding repeatedly selecting the same blocked oldest row. Cost if wrong: two small timeout columns are added by the task migration; legacy rows with no command marker retain prior behavior.
- Task 17: Ruling: Apply the existing 30-second step timeout option to RiskCheck as well as ledger steps, matching both production defaults and the mandated shortened unavailable-Risk test. Adjust the two-poller test to force its duration to zero together with due_at, because publication now correctly rebases the deadline. Cost if wrong: explicitly overridden step timeouts also affect RiskCheck.
- Task 17: Ruling: The outage test uses an explicit three-second interval only to establish the required ten timeouts of downtime; all delivery/completion checks use Eventually. Test fixtures emulate ledger replies after recovery, while the full real-service ledger proof remains T19. Cost if wrong: the focused test proves saga accounting rather than ledger integration.
- Task 18: Ruling: Reuse shared JWT/problem defaults; the registered Redis factory remains lazy and is never resolved by Gateway. Rate counters are in-process token buckets as specified. Use the standard YARP affinity/load-balancing/passive-health middleware with error mapping, no retry. Cost if wrong: effective rate scales with replicas, an explicit spec limitation.
- Task 18: Ruling: Enforce the 64-KiB limit for Content-Length and unknown-length bodies, buffering at most the bounded content before forwarding. Gateway readiness fetches signing keys and stays healthy after a successful fetch independently of downstream health. Cost if wrong: allowed unknown-length requests are buffered before proxying.
- Task 19: Ruling: Move channel readiness probing into the messaging assembly, retain service health behavior, and enforce private account balance mutation through ApplyPosting for both live posting and rebuild. Reflection guards were watched RED before these changes. Cost if wrong: Account exposes the single explicit posting method required by the plan.
- Task 19: Ruling: Prove the whole system on a fresh named Compose project so stable smoke keys cannot replay M1 money instead of executing the M2 bank/Risk path. Preserve repeatable keys for users with retained local data; an already captured merchant payment satisfies the prior authorization wait on replay. Stop only this project afterward without deleting volumes. Cost if wrong: the isolated proof retains its local volumes until explicitly removed.
- Final: Ruling: M3 telemetry/load/security expansion and failure suites remain scheduled after M2. Cost if wrong: users must not infer production telemetry/load certification from M2 completion.
- Final: Ruling: Phase 2 reporting/reconciliation and Kubernetes remain outside this milestone. Cost if wrong: those deployment and reporting capabilities are absent at this checkpoint.
- Final: Ruling: Production Keycloak hardening and real-acquirer compatibility remain repository non-goals. Cost if wrong: this local fake-bank portfolio system cannot be used as a production payment deployment.
- Final: Ruling: SMTP remains at-least-once and Gateway rate limits remain per instance, as explicitly accepted limitations. Cost if wrong: an email may duplicate after a crash, and aggregate rate limits scale with replicas.
- Final: Ruling: Keep in-flight Redis leases bounded at 30 seconds and completed metadata at 24 hours, with unique lease ownership for CAS completion/release. Legacy in-progress values have their excessive TTL reduced without extending an existing short TTL. Cost if wrong: a request still running after 30 seconds may overlap a retry; durable database keys and locks remain the safety guarantee.
- Final: Ruling: A missing command outbox row means its already confirmed, expired publication evidence was removed by processed-only retention; clear the marker and retry the due step normally. Cost if wrong: manual deletion of an unpublished row could consume an attempt, an administrative corruption outside normal retention.
- Final: Ruling: Serialize Risk evaluations by customer using a transaction advisory lock across currencies/days. The first test accidentally serialized while new Redis clients connected; warming both clients and awaiting disconnection produced the real RED with 11 approvals instead of 10 before the lock. Cost if wrong: one customer has serialized evaluation throughput; unrelated advisory hash collisions also serialize harmlessly.
- Final: Ruling: The reviewer left Gateway cancellation classification unproven. A new stalled-upstream regression observed 503 instead of 504, so promote it to an Important protocol finding. Inspect IHttpRequestTimeoutFeature.RequestTimeoutToken as well as the YARP error enum. Regression RED -> GREEN with full 504 RFC problem fields. Cost if wrong: genuine client disconnects remain transport failures, distinct from the gateway deadline.
